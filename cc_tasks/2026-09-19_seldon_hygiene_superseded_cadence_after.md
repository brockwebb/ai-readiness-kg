Prior art. 0.1: package managers and registries treat "replaced by" as a terminal, non-alarming status distinct from "broken" (npm `deprecated` with a successor, PEP 592 yanked releases, Debian `Replaces:`). 0.3: systemd's `After=` is an ordering-only declaration separate from `Requires=` (systemd.unit(5)), which is exactly `precedes` (order, not requirement); Make prerequisites and Airflow `set_upstream` declare order where the scheduler reads it, not in a comment. Nothing here is novel.

**Decisions taken here (operator overrides later):**

1. **One predicate, `decided_not_drifted(artifact, resolve)`, in `seldon/core/staleness.py`, used by every caller that lists or counts stale artifacts.** A `stale` artifact is *decided* when it carries a non-empty `withdrawn_reason`, or carries `superseded_by` naming (by `name` or artifact id) exactly one existing artifact that is not itself undecided-stale. A `superseded_by` that resolves to nothing, to more than one artifact, or to an undecided-stale artifact is **not** a decision: the artifact stays in the warning set and the detail line says why (`superseded_by 'X' does not resolve`). Chains are followed with a visited set; a cycle is undecided. `check_stale_artifacts` reports three counts (stale, withdrawn by decision, superseded by decision) and warns on the first only. `seldon go`, `seldon briefing` and `seldon status` use the same predicate, so "Stale Artifacts" means the same thing in all four. The Result state machine is not changed, for the reason the existing docstring gives.
2. **`seldon cadence` group with `list`, `check` and `render`.** `seldon cadence render (<cadence-name> | --template <path>) [--var key=value ...] [--period P] [--write] [--register]`. Without `--write` it prints to stdout and touches nothing. `--write` writes `cc_tasks/<instance_stem>.md` and refuses to overwrite. `--register` implies `--write` and calls the same registration function `seldon cc register` calls. The five `TEMPLATE_FIELDS` stay closed. Extra placeholders are legal only when the template declares them on a line within its first ten lines, `<!-- seldon:vars target, hosts -->`; a `--var` not declared, a declared var not supplied, and any other `{word}` outside a code fence that is neither a field nor a declared var each refuse with the name quoted. A hand render writes a `cadence_rendered` event (actor, template path, vars, instance stem), never `cadence_created`, so the log distinguishes a person asking from a schedule firing (DN-006 decision 8 keeps its meaning). `scripts/render_spot_scan.py` in ai-readiness-kg is **not** changed here: it derives the body's hosts from the frame, which Seldon cannot know. The RESULT says whether it could delegate to `seldon cadence render --var` byte-identically, with the diff if not.
3. **A machine-read `**After:**` header, read by `cc register`.** Grammar: `**After:** none` or `**After:** <ref>[, <ref> ...]`, where `<ref>` is a `cc_tasks` file stem (with or without `.md`) or an artifact id prefix of 8 or more hex characters. At registration each ref is resolved to exactly one ResearchTask (stem via the task's registered source path; prefix via id), and one `precedes` edge per ref is written through the existing `validate_precedes_write` / `add_chain` path, so self-loops and cycles are refused by the code that already refuses them. An unresolvable or ambiguous ref refuses the registration as `after_unresolved` with the grammar quoted and writes nothing, the same standing as `network_undeclared`. The header is optional: absent means no edges, as today. Re-registering is idempotent. `seldon_cc_register` (MCP) goes through the same function. A predecessor in a terminal state (`completed`, `verified`, `superseded`, `withdrawn`) still gets its edge; readiness already treats it as satisfied.
4. **SEQUENCING stays prose, and a lint catches the cross-task sentence.** `cc register` prints a warning (not a refusal) when the file has no `After` header and its SEQUENCING line matches `(not )?launched (before|after|until)` or names another `cc_tasks/*.md` stem. Seldon does not guess edges from a sentence.
5. **`CLAUDE.md` here, CC dispatch protocol section, one paragraph:** the `After` header, its grammar, and "sequencing between queued tasks is stated in `After`, not in the dispatch line and not only in SEQUENCING". The existing sentence "sequencing constraints between queued tasks are stated in the dispatch line, not assumed" is replaced by it. The Seldon repo's own docs get the same grammar wherever the three dispatch headers are documented.
