## Decisions

1. **Output root `docs/brief/`,** one generator script `scripts/build_brief_pack.py` that writes every file below and is idempotent (second run is a byte-for-byte no-op; a test asserts it, the same regenerate-and-compare guard the other views use). Each output file starts with a one-line comment naming the generator, the record's `generated_from` commit and the cycle of record. Numbers come from the record, the graph or registered Results, never typed.
2. **`B_usafacts_delta.md` and `.csv`.** The record has no `origin` field, so the delta is DERIVED and the derivation is stated at the top of the file: criteria A to D are USAFacts' four (kept as structure); E, F, G are additions (skeleton §5b, §5c, §5d say so and why); within A to D, USAFacts named criteria and gave no indicator-level tests (skeleton §1), so every indicator is an operationalization, marked `added (operationalizes <criterion>)`, with its type (AUTO/DOC/EVAL), measurement tier (M/O/D/unassigned), whether a rule exists (`rules_built`), and its access tier. Where the skeleton's §8 or an indicator note records a specific departure from or feedback to USAFacts, quote it in a `departure` column with the skeleton line reference. If any indicator has a `status` of candidate, withdrawn or dropped in the record, that is its mark. Do not invent a "changed" mark the record does not support; say the record cannot distinguish "kept verbatim" from "restated" and leave that column for the operator.
3. **`C_provenance.md` and `.csv`.** Per indicator: every `EVIDENCED_BY` document with its type (statute, OMB guidance, standard, W3C, research paper, vendor doc, from the manifest's `source_type`), whether the evidence cell carries a pinpoint locator (the same test `report_traceability.locators()` uses; quote the count, expected 8 of 49 before G4 and now whatever it measures), and the count of corpus documents per source type overall. A second section maps indicators to the federal policy instruments cited anywhere in the corpus (Evidence Act, M-25-05, M-23-22, Title 13, CIPSEA, SPD, DCAT-US): one row per instrument, the indicators that cite it. Honest coverage line at the top.
4. **`E_architecture.md`** with Mermaid diagrams, each generated or at least checked against the code, not drawn from memory: (a) operational view: agency site → harness fetch (identified UA, robots-first) → Observations → Rules → Findings → Results → report/site/MCP; (b) systems view: repos and processes (harness, event log shards, Neo4j projection, framework record and its single writer, Seldon graph, dispatcher, MCP server), with the one-owner-per-layer rule from CLAUDE.md; (c) data flow for one verdict: from URL to the Finding id and the retained body sha, using a real cell from the cycle of record as the worked example; (d) the judgement-generation model (re-judgement without re-fetch, DN-003). Each diagram is followed by a short "how to read it" and the file:line each box comes from. `mmdc` is not required; the Mermaid must parse (a test runs it through a parser if one is installed, else the RESULT says it was not validated).
5. **`D_demo_runbook.md`**: the offline demo from this machine, in order, each command copied from a file that already documents it (`docs/adopt/run_on_your_site.md`, `cc_tasks/2026-09-19_spot_scan_RESULT.md` §0, `docs/design/mcp_over_the_graph.md`): start Neo4j, `seldon go`, open the report, `score.py --body CENSUS`, `get_body`, `get_prescriptions`, `get_requirements`, a spot scan against the loopback fixtures (no federal host), and how a second agency would run it. Every command is executed once during this task with its first lines of output pasted under it; a command that fails is left in with its failure and a note, never deleted.
