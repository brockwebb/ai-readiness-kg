**Decisions taken here (operator overrides later):**
1. **Cadence lives in `seldon dispatch` as `seldon.yaml dispatch.cadence`**, a list of entries `{name, rule, template, instances_dir, last_instance}`. `rule` is a small closed vocabulary, not cron: `monthly_first_weekday: monday, at_utc: "00:00"` is the only rule needed today and the only one implemented; a second rule type is a code change with a test, not a string somebody types. The pass evaluates cadence before candidacy: for each entry that is due and has no instance file for the current period, it renders the template with `{cycle_name}`, `{period}`, `{cadence_name}` and `{created_at}` substituted, writes `cc_tasks/<date>_<name>_<period>.md`, registers it with the same code path as `seldon cc register`, records `last_instance`, and writes a `cadence_created` event (entry name, period, task id, file). Then the task flows through DN-006 decision 2 like any other. A period with an instance already on disk creates nothing; the check is the file, not the config field, so a hand-deleted `last_instance` cannot double-create.
2. **The template is `cc_tasks/templates/scan_cycle.md`, and it is a real task file.** Three headers (`**Spend:** zero model calls`, `**Network:** hosts, under cadence scan_cycle`, `**Framework layer served (DN-005 §5 rule 1):** §2.2 Tier M`), the immutability line, the addendum glob, sequencing, gate, report. Its body is the measured-cycle shape as cycle 4 ran it (`cc_tasks/2026-09-10_scan_run_4.md` and its RESULT are the source, not this file): freeze nothing new; run the harness over the FSS frame and the three reference hosts under the current `params.yaml` (the five-leg instrument after DD-066), one identified client, DD-032 rate limits; judge with the current rule set; publish Observations and Findings to the log as a new measured cycle under DN-003 (generation 1 of that cycle); write the cycle's matrices as data under `docs/reports/`; register the cycle's L0 Results in `proposed`; run `make gate-task`; RESULT; `seldon cc complete`; commit; push. **The template does not move the report's snapshot, the site's published Results, or the abstract.** A new measured cycle is on the log and in the matrices the moment it lands; promoting it to the published snapshot is a DN-004 decision that stays with the Desktop OODA until DN-005 §4 items 2 and 3 exist. The template says this in its own decisions block so a reader of cycle 5's task file knows what it will not do.
