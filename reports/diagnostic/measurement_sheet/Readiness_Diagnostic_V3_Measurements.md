# Readiness diagnostic: the measurements

*V3 of the readiness diagnostic; V2 is the sixteen-check page, V1 the criteria roll-up*

Generated by `scripts/measurement_sheet_build.py` from the framework record.

Each check is one measurement specification: what it asks, the instrument that reads it, what makes it pass, and where the expected behaviour comes from. The fields follow the ISO/IEC/IEEE measurement information model and its older, simpler form, Goal Question Metric.

## 1. Data offered as a file a program can read (A1)

| Field | Value |
|----------------------------|------------------------------------------------|
| Question | Is the data offered in a structured, machine-readable format? |
| What is examined | On the agency's data page, and the files linked from that page that sit on the same website as the page itself. |
| Instrument | httpx (httpx>=0.27); mode: auto |
| What the instrument reads | HTTP GET the product page; extract every download link; for each, HEAD and read Content-Type and file extension. Structured iff any of csv/json/parquet/xlsx/xml; PDF-only iff every link is application/pdf. |
| Evidence kept | response headers + link list + body sha256 |
| Passes when | A link on this data page, on the page's own website, returned a file that the server labeled by its media type, or the address named by its file extension, as a structured data format: CSV, JSON, XML, spreadsheet or Parquet. Every data page that was looked at met this. |
| Partial when | Some of the agency's data pages linked such a structured file and some did not. |
| Fails when, and what a fail does not claim | Every linked file on the same website, in the page's HTML as first served (files built by scripts or reached through a form are not seen), was checked, and none was labeled by its media type or its file extension as a structured data format. It is not a claim that the page links no structured file at all (a real data file served with a generic label and no extension is missed), nor that the agency publishes no machine-readable data: data offered on another website, such as a data portal or an API, or reached only through a query tool, is outside this page's same-website links. |
| Not measured when | The public client could not look at one or more of the linked files, for one of three reasons: the host refused the identified client; the client's own compliance with the site's robots.txt kept it from the file; or it could not confirm the absence because the page carried more same-website links than the cap of twenty-five, or a server or network error occurred. |
| Expected behaviour comes from | https://www.rfc-editor.org/rfc/rfc9110.txt<br>Data on the Web Best Practices (W3C Recommendation, 31 January 2017): "Make data available in a machine-readable, standardized data format that is well suited to its intended or potential use."<br>AI-Ready Data: Ensuring Public Data Meets the Needs of AI and the American Public, The USAFacts Guide to AI-Ready Data for Government Agencies: "Publish datasets in common structured formats (JSON, CSV, machine-readable Excel). Avoid documents (PDFs) that need to be processed and parsed."<br>M-25-05: Phase 2 Implementation of the Evidence Act, Open Government Data Access and Management: "data in a format that can be easily processed by a computer without human intervention"<br>M-25-05: Phase 2 Implementation of the Evidence Act, Open Government Data Access and Management: "Agencies must make each of their public data assets machine-readable." |
| Who else measures this | Google Lighthouse runs this kind of check: anyone can run its automated checks against a named page, its criteria are published, and a result comes back met, not met, or not applicable. It does not run this exact one. |
| Client | standard user; API user: Nothing: this check needs no key. |

## 2. The whole dataset in one download (A3)

| Field | Value |
|----------------------------|------------------------------------------------|
| Question | Can the whole dataset be retrieved in one request? |
| What is examined | On the agency's data page, and the files linked from that page that sit on the same website as the page itself. |
| Instrument | scrapy (scrapy>=2.11); mode: auto |
| What the instrument reads | Crawl the product page one hop; classify links as bulk (whole-product archive or full dataset file) vs filtered query. |
| Evidence kept | link graph + Content-Length per candidate |
| Passes when | This data page links, on its own website, an archive file (named by its extension) or a file that is not a web page, carries no query in its address, and is at least fifty kibibytes. It is not verified to be the complete product. Every data page that was looked at met this. |
| Partial when | Some of the agency's data pages linked such a whole-product download and some did not. |
| Fails when, and what a fail does not claim | Every linked file on the same website, in the page's HTML as first served (a download behind a script-driven button or a form is not seen), was checked, and none is an archive or a non-web-page file without a query of at least fifty kibibytes. The two tests are stand-ins: a link with a query may still deliver the whole product, and a complete product smaller than fifty kibibytes fails the size floor. It is not a claim that the agency's downloads are partial, nor that no bulk download exists elsewhere, such as a data portal, an FTP site, or a bulk endpoint on a data interface. |
| Not measured when | The public client could not look at one or more of the linked files, for one of three reasons: the host refused the identified client; the client's own compliance with the site's robots.txt kept it from the file; or it could not confirm the absence because the page carried more same-website links than the cap of twenty-five, or a server or network error occurred. |
| Expected behaviour comes from | Data on the Web Best Practices (W3C Recommendation, 31 January 2017): "Enable consumers to retrieve the full dataset with a single request."<br>OMB M-23-22: Delivering a Digital-First Public Experience: "making that information available as machine-readable data that can be accessed in bulk"<br>OMB M-23-22: Delivering a Digital-First Public Experience: "If an agency detects significant public interest in scraping information from web pages, the agency should strongly consider making that information available as machine-readable data that can be accessed in bulk" |
| Who else measures this | Google Lighthouse runs this kind of check: anyone can run its automated checks against a named page, its criteria are published, and a result comes back met, not met, or not applicable. It does not run this exact one. |
| Client | standard user; API user: Nothing: this check needs no key. |

## 3. The data page is in the site's list of pages (A5)

| What is examined | The sitemap files at the standard locations on the agency's own site (a sitemap, a sitemap index, and any sitemap the site's robots.txt names on that same site), plus an llms.txt and the well-known discovery paths. |
| Instrument | ultimate-sitemap-parser (ultimate-sitemap-parser>=1.0); mode: auto |
| What the instrument reads | HTTP GET /sitemap.xml (and the path robots.txt declares), /llms.txt, /.well-known/; parse the sitemap and test whether the product URL is covered. |
| Evidence kept | sitemap tree + coverage verdict for the product URL |
| Passes when | Every data page looked at was found listed: a sitemap served on the agency's own site carries the page's address exactly as the diagnostic records it. |
| Partial when | Some of the agency's data pages are listed in a served sitemap and some are not. |
| Fails when, and what a fail does not claim | For every data page looked at, the sitemaps served on the agency's own site were read and none lists the page's address in exactly the recorded form (a trailing slash, redirect target or query-string variant does not match), or the only discovery file served is an llms.txt (which by its proposal summarises a site rather than listing every page), or no sitemap is served at the standard locations; the reason names which. | Not measured when | The public client could not read one or more of the discovery files, for one of three reasons: the host refused the identified client, the client's own robots.txt compliance kept it from reading the file, or it could not confirm an absence or hit a server or network error. |

## 4. A published description of the agency's data service (A2)

| Field | Value |
|----------------------------|------------------------------------------------|
| Question | Does the agency publish a machine-readable description of its data API? |
| What is examined | At the data-interface address recorded for the agency in the project's records (read from the agency's own pages or seeded from a named source such as a developer page or a public catalog), and any description document recorded beside that address. |
| Instrument | httpx (httpx>=0.27); mode: auto |
| What the instrument reads | HTTP GET the documented API base and any OpenAPI/Swagger document; record auth scheme, declared rate limits, and whether the description is machine-readable. |
| Evidence kept | OpenAPI document + response headers |
| Passes when | A machine-readable OpenAPI or Swagger description document is served at the data-interface address recorded for this agency, and the result names that address. Every address that was looked at met this. |
| Partial when | Some of the recorded addresses served such a description and some did not. |
| Fails when, and what a fail does not claim | No OpenAPI or Swagger document was found at the data-interface addresses recorded for this agency; where no address is recorded at all, the fail says only that none was found in the sources searched. It is not a claim that the agency has no data interface, that its interface is undocumented, that it publishes no machine-readable description anywhere (a description at a developer page, or in another format such as a catalog document at the interface's root, is not looked for), or that its interface refuses programs. |
| Not measured when | The public client could not look at one or more recorded addresses, for one of three reasons: the host refused the identified client; the client's own compliance with the site's robots.txt kept it from the recorded address; or it could not confirm an absence because a recorded address was left unverified or a seed source unsearched, or a server or network error occurred. |

| Who else measures this | Google Lighthouse runs this kind of check: anyone can run its automated checks against a named page, its criteria are published, and a result comes back met, not met, or not applicable. It does not run this exact one. |

| Field | Value |
|----------------------------|------------------------------------------------|
| Question | Does the host's declared crawler policy let SI systems' crawlers fetch the data page? |
| What is examined | The single robots.txt file at the root of the agency's website, taken one host per agency. |
| Instrument | protego (protego>=0.3); mode: auto |
| What the instrument reads | HTTP GET /robots.txt; parse; evaluate Allow/Disallow for the product path per user-agent in the AI-crawler list (GPTBot, ClaudeBot, PerplexityBot, Google-Extended, CCBot, Bingbot). |
| Evidence kept | robots.txt body + sha256 + per-UA verdict |
| Passes when | The host's robots.txt, as stated, allows each of eight listed crawler tokens to fetch the data page's path. Every data page that was looked at met this. |
| Partial when | For some of the agency's data pages the stated policy allowed all eight listed crawler tokens and for some it did not. |
| Fails when, and what a fail does not claim | Either the host serves no robots.txt, which under the robots.txt standard actually permits every crawler, or its robots.txt tells at least one of the listed crawler tokens not to fetch the path. ## 6. The page labels itself as a dataset (A6)

| Field | Value |
|----------------------------|------------------------------------------------|
| Question | Does the data page carry structured markup that tells a machine it describes a dataset? |
| What is examined | The data page itself, reading the structured markup embedded in the page as it is served. |
| Instrument | extruct + pyshacl (extruct>=0.17); mode: auto |
| What the instrument reads | Extract embedded JSON-LD / microdata / RDFa from the product page; test for schema.org Dataset or DCAT; validate the DCAT graph against DCAT-AP SHACL shapes. |
| Evidence kept | extracted graph + SHACL report |
| Passes when | Every data page looked at carried markup, as served before any script runs, that declares a dataset with a name and a description (and any distribution it declares carries an access address). |

| Fails when, and what a fail does not claim | For every data page looked at, the markup as served before any script runs does not declare a dataset, or declares one that fails the minimal shapes (a name or description missing, or a declared distribution without an access address); the reason names the violation. It is not a claim that a dataset declared with a name and description is missing when the failing shape is the distribution's, nor that the agency's datasets are absent from dataset search, because catalog pages, data.gov records and other pages may carry the markup. |
| Not measured when | The public client could not read one or more pages, for one of three reasons: the host refused the identified client, the client's own robots.txt compliance kept it from reading the page, or the markup was declared but its graph could not be loaded to confirm the result, a server or network error. |

## 8. A front door built for programs (A9)

| Field | Value |
|----------------------------|------------------------------------------------|
| Question | Does the agency serve an entry point built for machine clients (an API description, an agent-protocol endpoint, an llms.txt) where such clients look first? |
| What is examined | A fixed handful of machine addresses this project checks on the agency's site: the recorded API base and its description, the /.well-known/mcp path, and /llms.txt. |
| Instrument | httpx (httpx>=0.27); mode: auto |
| What the instrument reads | Probe for a machine-first entry point: OpenAPI at the documented base, /.well-known/mcp or an advertised MCP/A2A endpoint, /llms.txt. |
| Evidence kept | probe matrix + any served descriptor |
| Passes when | For every data page looked at, at least one of the addresses this project checks returned content that is not an HTML page. |
| Partial when | For some of the agency's data pages at least one checked address returns non-HTML content and for some none does. |
| Fails when, and what a fail does not claim | For every data page looked at, none of the handful of addresses this project checks, by a plain request with no key and no accept header, returned non-HTML content. | Not measured when | The public client could not read one or more addresses, for one of three reasons: the host refused the identified client, the client's own robots.txt compliance kept it from reading, or the recorded API base could not be reached to confirm an absence, a server or network error. |
| Expected behaviour comes from | not specified |
| Who else measures this | No public tool runs this exact check. |
| Client | standard user; API user: This check requests with no key, so a registered public client that presents a key could change the result here: an API that answers only a key-bearing request could return machine content on a second look where the bare request got an HTML or error page. |
